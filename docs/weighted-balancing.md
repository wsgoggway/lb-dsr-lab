# Взвешенное распределение трафика на L3/L4 (pf): механизм и план pfkeeper v1.1

Статус: дизайн проверен живым PoC на стенде 2026-10-22; интеграция в pfkeeper — v1.1 (в v1 веса не входят сознательно).

## 1. Задача и ограничение pf

Требуется распределять трафик по бэкендам DSR-кластера не поровну, а пропорционально весам
(типовой случай: разноразмерные узлы, канареечный вывод нового бэкенда).

pf на FreeBSD 14 не умеет веса напрямую:

- **Таблица — это множество адресов.** Дубликаты при `-T add` схлопываются в одну запись,
  поэтому «добавить адрес трижды для веса 3» невозможно.
- У `route-to` есть только режимы пула: `bitmask`, `random`, `source-hash`, `round-robin` —
  все равнодолевые, ключа `weight` не существует (в отличие от relayd/HAProxy).
- relayd отклонён осознанно (решение по проекту — чистый pf), L7-прокси ломают DSR
  (бэкенд должен отвечать клиенту напрямую с src=VIP).

## 2. Механизм: цепочка probability-правил

`man pf.conf` даёт правило фильтрации атрибут `probability <number>%` (0..1, границы не
включены; дробные значения принимаются — проверено `12.5%`). Семантика: если случайная
проверка не прошла, правило **не считается сработавшим** и оценка правил продолжается
дальше — даже при `quick`. Это позволяет собрать цепочку:

```pf
# веса rs1:rs2:rs3 = 5:3:2 (50% / 30% / 20%)
pass in quick on vtnet0 route-to (vtnet0 192.168.100.21) proto tcp to 192.168.100.200 port 80 probability 50% keep state (sloppy)
pass in quick on vtnet0 route-to (vtnet0 192.168.100.22) proto tcp to 192.168.100.200 port 80 probability 60% keep state (sloppy)
pass in quick on vtnet0 route-to (vtnet0 192.168.100.23) proto tcp to 192.168.100.200 port 80 keep state (sloppy)
```

Формула для i-го члена отсортированного по убыванию веса списка:
**p_i = w_i / (w_i + w_{i+1} + … + w_N)** — вероятность считается от остатка трафика,
не от полного потока (для rs2 выше: 3/5 = 60% оставшихся 50% = 30% общего).
Последнее правило — **всегда безусловное** (catch-all): остаток вероятности обязан
уйти в DSR-маршрутизацию. Решение принимается на первом пакете соединения
(дальше соединение живёт в state, поэтому распределение per-connection).

## 3. Результаты PoC (живой стенд, client → VIP:80, 1000/300 соединений)

| Конфиг (rs1:rs2) | Замер rs1/rs2 | Отклонение |
|---|---|---|
| probability 70% + catch-all | 678 / 322 | ±2% от целевого |
| probability 90% + catch-all | 888 / 112 | ±1% |
| 90% без catch-all (rs2 «удалён» из цепочки) | 278 rs1 + **22 без ответа** | утечка 7.3% |
| один безусловный catch-all (rs2 down, кейс дренирования) | 300 / 0 | ровно |

Выводы из PoC:

1. Веса держатся в пределах статистической погрешности; смена весов применяется
   атомарным `pfctl -f` без обрыва живых соединений (state сохраняется).
2. **Catch-all обязателен.** Правило `probability P%` без безусловного замыкающего
   правила пропускает остаток (100−P)% мимо weighted-цепочки — пакет остаётся на
   балансировщике без сервиса (в PoC — 22/300 отказов).
3. `sticky-address` с весами несовместим по смыслу: sticky прикрепляет источник к пулу,
   и замер с одного клиента даёт 0/100 вместо 70/30. Для per-source аффинности при
   весах см. §5 (режим sticky).
4. Грабля проверки конфига: FreeBSD pfctl не принимает `pfctl -nf -f file` — склеенный
   `-nf` съедает `-f` как своё значение, файл становится лишним аргументом
   («unknown command line argument»). Правильно: `pfctl -n -f file`.
5. Дробные проценты (`12.5%`) pfctl принимает — точности хватает на любые
   практические соотношения весов.

## 4. Почему не другие варианты

| Вариант | Почему нет |
|---|---|
| Дубликаты в таблице `<webs>` | pf-таблица — множество, дубликаты схлопываются |
| Несколько таблиц + round-robin | даёт только равные доли между таблицами, веса не выражает |
| relayd с weight | отклонён на старте проекта: чистый pf; relayd не DSR-transparent в нашей схеме |
| nginx/HAProxy L7 | прокси-режим ломает DSR (ответ должен идти мимо балансировщика) |
| Сплит по подсетям/DSCP/интерфейсам | делит по признаку клиента, а не по весу бэкенда |

## 5. Интеграция в pfkeeper v1.1

Веса — надстройка над существующей архитектурой (таблицы + health + peer-sync), а не новая подсистема.

### Схема стейта (git)

```yaml
# state/services/web.yaml — НОВЫЙ объект: сервис с взвешенным правилом DSR
service: web
table: webs                 # члены и health берутся из существующей таблицы
mode: weighted              # round-robin (как сейчас) | weighted
listen: { iface: vtnet0, vip: 192.168.100.200, port: 80, proto: tcp }
sticky: false               # false = per-connection веса (по умолчанию)
                            # true  = + sticky-address, аффинность по источнику
```

```yaml
# state/tables/webs.yaml — добавляется одно поле
members:
  - addr: 192.168.100.21
    weight: 5               # 1..100, default 1; 0 = drain (член здоров, но трафика не получает)
  - addr: 192.168.100.22
    weight: 3
```

Валидация: weight ∈ [0..100]; в mode=weighted таблица должна иметь ≥1 члена с weight>0.

### Рендер и apply

- MASTER при каждом reconcile рендерит якорный фрагмент из
  `(members × weight) ∩ healthy` по формуле §2, сортировка по весу по убыванию,
  последнее правило — безусловное. Рендер детерминирован — BACKUP получает тот же
  фрагмент через существующий `PushConfig` verbatim, `SyncCheck` ловит любые расхождения.
- Режим `round-robin` рендерит текущее правило (таблица + round-robin sticky-address) —
  обратная совместимость с фазами 1–2 без изменений поведения.
- Health-переход уже сегодня триггерит apply; в weighted-режиме он дополнительно
  перерендеривает цепочку: выбывший член просто не получает правила, веса здоровых
  ренормализуются автоматически формулой (дренаж демо-кейса §3.3 превращается в
  корректный catch-all на оставшихся).
- Смена весов: как существующие мутации — gRPC → git-коммит (actor из CN) → apply → push пиру.
- Sticky=true: правило получает `sticky-address`; смена весов при активном sticky требует
  сброса sticky-записей (процедура из фазы 1: двойной `pfctl -k 0.0.0.0/0 -k 0.0.0.0/0`
  + `-F Sources`), otherwise новые веса видят только новые источники.

### Наблюдаемость

- Новая метрика `pfkeeper_service_rule_rendered{service, member, probability}` (gauge, %);
  желаемое распределение выводится из неё; фактическое на L3 не измеряется балансировщиком
  (счётчики были бы на бэкендах).
- Попутный фикс найденного дефекта: `Metrics.SetPeer` не вызывается никем
  (`peer_reachable` / `peer_divergence` / `peer_lag_seconds` висят на нулях с релиза) —
  проводка из `peer.Controller.tickOnce` в v1.1.

### Тест-план v1.1

- t13: замер распределения 5:3:2 (≥1000 соединений, допуск ±3%) + смена весов на лету.
- t14: health ∩ weight — падение rs1 (fall=3) → цепочка перерендеривается, dоля rs2/rs3
  растёт пропорционально, возврат восстанавливает; консенсус `and` — сверка на обоих узлах.
- t15: sticky=true — один источник держит бэкенд; смена весов + flush sticky.
- t16: peer — вес коммитится через BACKUP → прокси на MASTER → одинаковые якоря на паре;
  ручной дрифт якоря → SyncCheck → heal.

### Не входит в v1.1

Плавный drain (перелив соединений с уменьшаемого члена без обрыва — live-connections
и так доживают в state, речь только о новых), веса в NAT-режиме (rdr-пул имеет те же
равнодолевые пулы — механизм переносится 1:1 при необходимости), ECMP/multipath.
