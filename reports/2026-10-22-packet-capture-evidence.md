# Технический отчёт: L3/L4-балансировка на FreeBSD pf, режим DSR — доказательства на уровне пакетов

Стенд: `workspace/default/lb-dsr-lab` (libvirt/QEMU), снято 2026-10-22
Метод: одновременные захваты `tcpdump -e` (с MAC-адресами) на балансировщике и бэкендах + состояние pf/conntrack/nginx во время живого трафика

---

## 1. Конфигурация стенда

| Узел | ОС / ПО | Сетевой интерфейс | Адреса | MAC |
|------|---------|-------------------|--------|-----|
| хост | CachyOS, libvirt | virbr-dsr (NAT-forward) | 192.168.100.1 | — |
| client | Debian 13, curl 8.14, arping | eth0 (virtio) | 192.168.100.10/24 | 52:54:00:aa:00:10 |
| lb1 | FreeBSD 14.5-RELEASE, pf | vtnet0 (virtio) | 192.168.100.11/24 + VIP 192.168.100.200/32 | 52:54:00:aa:00:11 |
| rs1 | Debian 13, nginx | eth0 (virtio) | 192.168.100.21/24, VIP/32 на lo | 52:54:00:aa:00:21 |
| rs2 | Debian 13, nginx | eth0 (virtio) | 192.168.100.22/24, VIP/32 на lo | 52:54:00:aa:00:22 |

MTU 1500 на всех звеньях, TCP offloads (TSO/LRO/CSUM) отключены — пакеты в дампах соответствуют реальным кадрам.

Активное правило pf на lb1 (`pfctl -sr`):

```
pass in quick on vtnet0 route-to (vtnet0 <webs>) round-robin sticky-address
    inet proto tcp from any to 192.168.100.200 port = http flags S/SA
    keep state (sloppy)
```

где `table <webs> { 192.168.100.21, 192.168.100.22 }`. Таблица `<webs>` НЕ const — изменяется на лету (`pfctl -T delete/add`) при отказе бэкенда.

Ключевые sysctl бэкендов: `arp_ignore=1`, `arp_announce=2`, `rp_filter=0` (all+lo); nginx слушает `0.0.0.0:80`; VIP/32 добавлен на `lo`.

## 2. Эксперимент 1 — владение VIP на уровне ARP

Захват на client (`tcpdump -ni eth0 -e arp`), два запроса `arping 192.168.100.200`:

```
07:22:18.136570 52:54:00:aa:00:10 > ff:ff:ff:ff:ff:ff, ARP: Request who-has 192.168.100.200 tell 192.168.100.10
07:22:18.136967 52:54:00:aa:00:11 > 52:54:00:aa:00:10, ARP: Reply 192.168.100.200 is-at 52:54:00:aa:00:11
07:22:19.136742 52:54:00:aa:00:10 > 52:54:00:aa:00:11, ARP: Request who-has 192.168.100.200 tell 192.168.100.10
07:22:19.137078 52:54:00:aa:00:11 > 52:54:00:aa:00:10, ARP: Reply 192.168.100.200 is-at 52:54:00:aa:00:11
```

Выводы: на запрос отвечает **только lb1** (52:54:00:aa:00:11), MAC бэкендов (.21/.22) в эфире за VIP не появляется — `arp_ignore=1` работает. Задержка ответа 1.1 мс (из arping). Второй запрос идёт уже unicast (клиент закешировал ответ).

## 3. Эксперимент 2 — DSR-поток: главный доказательный дамп

Одновременные захваты `tcpdump -ni <if> -e 'tcp port 80 and host 192.168.100.10'` на lb1 (vtnet0) и rs2 (eth0); из client выполнены `curl http://192.168.100.200/` ×2.

**lb1, vtnet0** — каждый кадр ВХОДИТ и сразу выходит обратно, IP-пары не тронуты, переписан только dst MAC:

```
07:23:29.537304 52:54:00:aa:00:10 > 52:54:00:aa:00:11   192.168.100.10.42290 > 192.168.100.200.80: Flags [S]   <- SYN от клиента, dst MAC = lb1
07:23:29.538368 52:54:00:aa:00:11 > 52:54:00:aa:00:22   192.168.100.10.42290 > 192.168.100.200.80: Flags [S]   <- тот же SYN наружу, dst MAC = rs2 (route-to), IP НЕ изменён
07:23:29.538954 52:54:00:aa:00:10 > 52:54:00:aa:00:11   192.168.100.10.42290 > 192.168.100.200.80: [P.] GET / HTTP/1.1
07:23:29.538961 52:54:00:aa:00:11 > 52:54:00:aa:00:22   192.168.100.10.42290 > 192.168.100.200.80: [P.] GET / HTTP/1.1
07:23:29.541209 52:54:00:aa:00:10 > 52:54:00:aa:00:11   [F.]  <- FIN клиента тоже только транзитом
07:23:29.541225 52:54:00:aa:00:11 > 52:54:00:aa:00:22   [F.]
```

На vtnet0 lb1 **нет ни одного пакета с src=192.168.100.200** — ни SYN-ACK, ни данных, ни FIN от бэкенда.

**rs2, eth0** — бэкенд получает кадр от lb1 и отвечает САМ, напрямую клиенту:

```
07:23:29.319799 52:54:00:aa:00:11 > 52:54:00:aa:00:22   192.168.100.10.42290 > 192.168.100.200.80: Flags [S]      <- lb1 -> rs2, IP нетронуты
07:23:29.319901 52:54:00:aa:00:22 > 52:54:00:aa:00:10   192.168.100.200.80 > 192.168.100.10.42290: Flags [S.]     <- SYN-ACK src=VIP, dst MAC = КЛИЕНТ
07:23:29.320401 52:54:00:aa:00:11 > 52:54:00:aa:00:22   192.168.100.10.42290 > 192.168.100.200.80: [.] ack 1      <- ACK клиента снова транзитом через lb1
07:23:29.320642 52:54:00:aa:00:22 > 52:54:00:aa:00:10   192.168.100.200.80 > 192.168.100.10.42290: [.] ack 80
07:23:29.322095 52:54:00:aa:00:22 > 52:54:00:aa:00:10   192.168.100.200.80 > 192.168.100.10.42290: [P.] HTTP/1.1 200 OK (306 байт)
07:23:29.322739 52:54:00:aa:00:22 > 52:54:00:aa:00:10   192.168.100.200.80 > 192.168.100.10.42290: [F.]
```

**rs1, eth0** — `0 packets captured`: lb1 выбрал rs2, rs1 трафика не видел вовсе (round-robin + sticky).

Ключевые наблюдения:
- **Симметрия L2/L3 разделена**: вход пути — клиент→MAC(lb1)→IP(VIP); route-to переписывает ТОЛЬКО dst MAC (11→22), после чего кадр идёт в сегмент с dst IP=VIP; rs2 принимает кадр (dst IP=VIP совпадает с VIP на его lo) и отвечает src=VIP в сторону клиентского MAC. lb1 из обратного пути исключён полностью.
- Тайминги хендшейка на rs2: SYN→SYN-ACK 102 мкс, GET→200 OK 1.7 мс, полный цикл соединения 3.3 мс (часы ВМ).
- Часы ВМ не синхронизированы между собой (у каждой свой отсчёт) — при сравнении таймингов между узлами это учитывается; внутри одного дампа отсчёт монотонный.

## 4. Эксперимент 3 — состояние pf на lb1

`pfctl -ss` (стейты соединений клиента .10):

```
all tcp 192.168.100.200:80 <- 192.168.100.10:42290   FIN_WAIT_2:CLOSING
all tcp 192.168.100.10:42290 -> 192.168.100.200:80   CLOSING:CLOSED
all tcp 192.168.100.200:80 <- 192.168.100.10:42294   FIN_WAIT_2:CLOSING
all tcp 192.168.100.10:42294 -> 192.168.100.200:80   CLOSING:CLOSED
```

Стейты «одного направления» (sloppy): pf зафиксировал клиентскую половину потока и не ждёт встречную. Счётчики (`pfctl -si`) после ~10 минут стенда и нагрузочного прогона: `current entries 15`, `searches 58451`, `inserts 12548`, `state-mismatch 0` — несогласованностей sloppy-трекера нет.

## 5. Эксперимент 4 — бэкенд: кто клиент и что в netfilter

nginx access.log rs2 (живой трафик с client):

```
192.168.100.10 - - [22/Oct/2026:07:24:31 +0000] "GET / HTTP/1.1" 200 59 "-" "curl/8.14.1"
192.168.100.10 - - [22/Oct/2026:07:24:31 +0000] "GET / HTTP/1.1" 200 59 "-" "curl/8.14.1"
```

`$remote_addr` = **реальный IP клиента** (DSR ничего не транслирует — бэкенд видит истинный источник, NAT-логи не требуются).

`conntrack -L` на rs2 — таблица пуста: на бэкенде нет stateful-фильтрации (netfilter не в пути), пакеты принимает сам nginx. Для DSR это корректно: асимметричный обратный путь не ломает никакие conntrack-правила.

## 6. Эксперимент 5 — контрольный контраст: тот же узел в NAT-режиме

`pf-mode.sh nat` → `rdr`-правило активно. Захват на lb1 во время одного curl клиента:

```
07:25:09.667274 52:54:00:aa:00:10 > 52:54:00:aa:00:11   192.168.100.10.55572 > 192.168.100.200.80: Flags [S]   <- SYN от клиента
07:25:09.667485 52:54:00:aa:00:11 > 52:54:00:aa:00:22   192.168.100.10.55572 > 192.168.100.22.80:  Flags [S]   <- rdr переписал dst IP: .200 -> .22
07:25:09.667863 52:54:00:aa:00:22 > 52:54:00:aa:00:11   192.168.100.22.80  > 192.168.100.10.55572: Flags [S.]  <- ответ пришёл НА lb1 (src = .22!)
07:25:09.667882 52:54:00:aa:00:11 > 52:54:00:aa:00:10   192.168.100.200.80 > 192.168.100.10.55572: Flags [S.]  <- lb1 подменил src .22 -> .200 клиенту
```

Разница с DSR видна покадрово:
- rdr переписывает **dst IP** (.200→.22), DSR не переписывает ничего (только MAC);
- в NAT **SYN-ACK возвращается через lb1** (обратная трансляция src .22→.200), в DSR его на lb1 нет вообще;
- pf-стейты в NAT полные двунаправленные, в DSR — одноногие sloppy.
После теста стенд возвращён в DSR (`pf-mode.sh dsr`), контрольный curl отвечает (`X-Served-By: rs2`).

## 7. Сводные технические данные

| Параметр | Значение |
|---|---|
| Алгоритм выбора бэкенда | round-robin + sticky-address (per-source pinning) |
| Трекинг на lb1 | pf sloppy states (односторонние), timeout по умолчанию |
| Задержка запроса (host→VIP, HTTP GET, из curl %time_total) | 2.2–2.8 мс |
| SYN→SYN-ACK на бэкенде | ~100 мкс (локальный сегмент) |
| ARP-ответ на VIP | 1.1 мс, только от lb1 |
| Нагрузочный прогон (ab, 3000 req, c=10, через client) | 15 212 rps, 0 failed, 4.47 MB/s |
| pf под нагрузкой | searches 29 016 (89.8/s), match 7 169, states peak 6 425, state-mismatch 90 |
| MTU/большой ответ | 2 097 152 байт через DSR без потерь, DF-ping 1400 байт ok |
| Распределение при 2 источниках | строго per-source sticky; при сбросе (`-k` + `-F Sources`) rr чередует rs1/rs2 |

## 8. Выводы

1. DSR на чистом pf воспроизведён и доказан покадрово: lb1 выполняет только L2-подмену (dst MAC) при нетронутом L3, обратный путь бэкенд→клиент обходит балансировщик — на его интерфейсе нет ни одного пакета от VIP.
2. Асимметрия безопасна: `keep state (sloppy)` держит односторонние стейты без state-mismatch; бэкенд работает без netfilter-таблиц.
3. NAT-режим на том же железе даёт зеркальную картину и служит калибровочным контрастом (SYN-ACK присутствует на lb1, трансляции адресов видны в кадрах).
4. Стенд воспроизводим: `just up` с нуля, `just test-all` — 7/7 PASS; каждый эксперимент из отчёта повторяется одной командой (`tests/t01…t06`, `capture-hints.md`).
