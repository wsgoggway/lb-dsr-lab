# Технический отчёт: испытания L3/L4-балансировки на FreeBSD pf (DSR, CARP, pfsync)

Испытательный период: 2026-10-21…2026-10-22. Стенд: 5 ВМ на libvirt/QEMU (KVM).
Версии: FreeBSD 14.5-RELEASE (pf, carp, pfsync), Debian 13 (nginx, cloud-init), libvirt/QEMU, tcpdump 4.99/5.x, ab (ApacheBench).

---

## 1. Конфигурация объекта испытаний

| Узел | ОС | Сегмент/интерфейс | Адрес | MAC |
|---|---|---|---|---|
| client | Debian 13, curl 8.14, arping | net-dsr / eth0 | 192.168.100.10/24 | 52:54:00:aa:00:10 |
| lb1 | FreeBSD 14.5-RELEASE, pf | net-dsr / vtnet0; net-sync / vtnet1 | 192.168.100.11/24; 10.0.100.1/30 | 52:54:00:aa:00:11 / 01:11 |
| lb2 | FreeBSD 14.5-RELEASE, pf | net-dsr / vtnet0; net-sync / vtnet1 | 192.168.100.12/24; 10.0.100.2/30 | 52:54:00:aa:00:12 / 01:12 |
| rs1 | Debian 13, nginx | net-dsr / eth0 | 192.168.100.21/24 + VIP/32 на lo | 52:54:00:aa:00:21 |
| rs2 | Debian 13, nginx | net-dsr / eth0 | 192.168.100.22/24 + VIP/32 на lo | 52:54:00:aa:00:22 |
| VIP | — | CARP vhid 1 (пара lb1/lb2) | 192.168.100.200/32 | 00:00:5e:00:01:01 |

Сеть: libvirt net-dsr (NAT-forward, мост virbr-dsr, 192.168.100.0/24, хост .1), net-sync (без L3, мост virbr-sync, 10.0.100.0/30). MTU 1500; TCP offloads (tso/lro/rxcsum/txcsum) отключены на всех интерфейсах. Адресация статическая (cloud-init network-config v2).

Правило балансировки pf (единый ruleset пары, FreeBSD-синтаксис):

```
table <webs> { 192.168.100.21, 192.168.100.22 }
pass in quick on vtnet0 route-to (vtnet0 <webs>) round-robin sticky-address \
    proto tcp to 192.168.100.200 port 80 keep state (sloppy)
pass in quick proto carp keep state (no-sync)
pass in quick proto pfsync keep state (no-sync)
```

CARP: vhid 1, advbase 1, advskew 0 (lb1) / 100 (lb2), пароль общий, `net.inet.carp.preempt=1`. pfsync: syncdev vtnet1, syncpeer — адрес парного узла, version 1400.

Бэкенды: `arp_ignore=1`, `arp_announce=2`, `rp_filter=0` (all/lo/default), nginx `listen 80`, `X-Served-By: $hostname`, `/healthz`, маркерная страница 59 B.

## 2. Методика

- Захваты пакетов: `tcpdump -ni <if> -e` (с MAC-адресами) одновременно на lb1 (vtnet0), rs1/rs2 (eth0), client (eth0); фоновый запуск через nohup, стоп по pid.
- Состояние фильтра: `pfctl -ss/-si/-sr/-t webs -T show` на балансировщиках; `conntrack -L` на бэкендах.
- Прикладной уровень: заголовок `X-Served-By`, nginx access.log, /healthz.
- Нагрузка: ab -n 3000 -c 10 (client → VIP).
- Управление режимами: замена /etc/pf.conf + `pfctl -f` (DSR ↔ NAT) через `scripts/pf-mode.sh`.
- Отказоустойчивость: останов nginx на бэкенде (`systemctl stop nginx`), выключение lb1 (`shutdown -p now`) под непрерывным curl-циклом 120 запросов (curl -m 2, интервал 0.1 c) с подсчётом ok/fail.

## 3. Результаты испытаний фазы 1 (один балансировщик)

### 3.1 ARP-владение VIP

Захват на client, `arping -c 2 192.168.100.200`:

```
Request who-has 192.168.100.200 tell 192.168.100.10          (broadcast)
Reply 192.168.100.200 is-at 52:54:00:aa:00:11                 (только lb1)
Request who-has 192.168.100.200 tell 192.168.100.10          (unicast повтор)
Reply 192.168.100.200 is-at 52:54:00:aa:00:11
```

Откликов от MAC бэкендов (.21/.22) — 0. Задержка ответа 1.1 мс.

### 3.2 Трансляция потока на L2 (DSR)

Одновременный захват lb1/vtnet0 и rs2/eth0, curl от .10 (порт клиента 42290):

| № | Узел | Кадр (MAC) | Пакет (IP) | Флаги |
|---|---|---|---|---|
| 1 | lb1 | 00:10 → 00:11 | .10.42290 > .200.80 | SYN |
| 2 | lb1 | 00:11 → 00:22 | .10.42290 > .200.80 | SYN |
| 3 | rs2 | 00:11 → 00:22 | .10.42290 > .200.80 | SYN |
| 4 | rs2 | 00:22 → 00:10 | .200.80 > .10.42290 | SYN-ACK |
| 5 | rs2 | 00:22 → 00:10 | .200.80 > .10.42290 | P. HTTP 200 (306 B) |
| 6 | rs2 | 00:22 → 00:10 | .200.80 > .10.42290 | FIN |

На vtnet0 lb1 пакеты с src=192.168.100.200 — **0** (за прогон: 52 SYN, 0 SYN-ACK). lb1 меняет только dst MAC (00:11→00:22, кадры 1→2); IP-пары не изменяются. SYN→SYN-ACK на rs2 — 102 мкс; GET→200 — 1.7 мс; полный цикл соединения — 3.3 мс.

### 3.3 Состояние pf

```
all tcp 192.168.100.200:80 <- 192.168.100.10:42290   FIN_WAIT_2:CLOSING
all tcp 192.168.100.10:42290 -> 192.168.100.200:80   CLOSING:CLOSED
```

Однонаправленные (sloppy) стейты; счётчики: searches 58 451, inserts 12 548, state-mismatch 0.

### 3.4 Источник на бэкенде

nginx access.log rs2: `192.168.100.10 - - [...] "GET / HTTP/1.1" 200 59` — реальный IP клиента без трансляций. `conntrack -L` на rs2 — таблица пуста: stateful-фильтрация на бэкенде не используется, асимметрию обратного пути нечему нарушать.

### 3.5 Привязка по источнику (sticky)

40 запросов с хоста (.1) → rs1 40/40; 10 запросов с client (.10) → rs2 10/10. После сброса (`pfctl -k 0.0.0.0/0 -k 0.0.0.0/0; pfctl -F Sources`) чередование rs1/rs2/… по round-robin.

### 3.6 Отказ бэкенда

| Шаг | Действие | Результат (6 запросов host+client) |
|---|---|---|
| baseline | nginx rs1 работает | ответ rs1, 2.5 мс |
| pin | source tracking сброшен, host прибит к rs1 | host → rs1 |
| отказ | `systemctl stop nginx` на rs1 | **0 ok / 3 fail** (pinned-источник) |
| вывод из пула | `pfctl -t webs -T delete 192.168.100.21` + сброс | **6 ok / 0 fail**, 2.3–2.8 мс |
| возврат | `-T add` + старт nginx | ответ rs2/rs1, 2.5 мс |

### 3.7 MTU / крупные ответы

`curl` 2 097 152 байт через VIP → size_download = 2 097 152 (расхождение 0); `ping -M do -s 1400` до VIP — 100%.

### 3.8 Контрольный режим NAT (тот же узел)

Захват lb1 при одном запросе:

```
.10.55572 > .200.80: [S]        (вход)
.10.55572 > .22.80:  [S]        (rdr переписал dst: .200 → .22)
.22.80  > .10.55572: [S.]       (ответ пришёл на lb1, src = .22)
.200.80 > .10.55572: [S.]       (lb1 подменил src обратно на VIP)
```

Синтетический контраст с DSR: в NAT SYN-ACK присутствует на lb1, стейты двунаправленные (44 шт.), трансляции адресов видны в кадрах.

### 3.9 Нагрузка

ab (client → VIP): Complete 3000, Failed 0, **15 212.52 rps**, 0.657 мс/запрос, 4.47 MB/s. pf в ходе прогона: searches 29 016 (89.8/с), match 7 169, пиковое число стейтов 6 425, state-mismatch 90 (0.3/с). Load average lb1 — 0.66.

## 4. Результаты испытаний фазы 2 (CARP-пара + pfsync)

### 4.1 Выборы и роли

```
lb1: carp: MASTER vhid 1 advbase 1 advskew 0
lb2: carp: BACKUP vhid 1 advbase 1 advskew 100
```

Ровно один MASTER на пару; `net.inet.carp.preempt = 1` на обоих узлах.

### 4.2 Виртуальный MAC

```
arping 192.168.100.200 → Unicast reply [00:00:5E:00:01:01]  1.093 мс / 1.327 мс
```

Реальные MAC узлов (.11/.12) за VIP в эфире отсутствуют.

### 4.3 Репликация состояния (pfsync)

После 10 запросов: стейты с участием клиента — lb1: 20, lb2: 14 (в т.ч. идентичная запись `.200:80 <- .10:49814 FIN_WAIT_2:CLOSING`). Кадры на vtnet1:

```
10.0.100.1 > 10.0.100.2: PFSYNCv5 len 1413
10.0.100.1 > 10.0.100.2: PFSYNCv5 len 582
```

### 4.4 Отказ балансировщика под нагрузкой (t07)

Клиентский цикл 120 запросов; lb1 выключен в середине цикла (`shutdown -p now`):

| Метрика | Значение |
|---|---|
| Успешных | **119 / 120** |
| Неуспешных (curl timeout 2 c) | **1** |
| Роль lb2 после переключения | carp: MASTER advskew 100 |
| Время простоя | ≈ 2 с (advbase 1 + advskew) |

### 4.5 Восстановление

lb1 запущен повторно: загрузка ≈ 2 мин, `carp: BACKUP advskew 0` → с `preempt=1` возврат MASTER; контроль: ровно один MASTER на пару; контрольный запрос к VIP успешен.

## 6. Дефекты, выявленные при испытаниях и устранённые

| Симптом | Причина | Устранение |
|---|---|---|
| ВМ не загружается, диск «пуст» | libvirt `vol-create-as` без `--backing-format` создавал оверлей с backing=raw | полные копии образов (`vol-create-as` + `vol-upload`) |
| Гости без адресов | ufw хоста резал guest→host (UDP 67/68, DNS) | `ufw allow in on virbr-dsr` + `ufw route allow in/out on virbr-dsr` |
| CARP-алиас не встал | `carp.ko`/`pfsync.ko` — модули, не в GENERIC | `kldload carp/pfsync` + `kld_list="carp pfsync"` |
| lb1 без второй NIC | `virsh undefine` UEFI-домена требует `--nvram` | `undefine --nvram` + redefine (проверка: 2 × `<interface `) |
| pf.conf «syntax error» | FreeBSD-грамматика: `route-to` сразу после `on <if>`; `keep state (...)` — последний элемент | перенос route-to и keep state; однострочные правила |
| Синтаксис-ошибка в pf.conf без видимой причины | пробел после `\` переноса строки | отказ от переносов |
| tcpdump-фильтр ловил только SYN-ACK | `(tcp-syn|tcp-ack) == (tcp-syn|tcp-ack)` требует оба бита | фильтр `tcp port 80` + разбор по Flags |
| Sticky не сбрасывается | одиночный `-k` оставлял обратную половину стейтов | `pfctl -k 0.0.0.0/0 -k 0.0.0.0/0` + `-F Sources`; `-F all` запрещён (сносит ruleset) |
| NAT-режим: RST вместо ответа | rdr переписывает dst на собственный IP бэкенда, nginx слушал только VIP | `listen 80` (wildcard) + restart (reload не перевязывает сокет) |
| pfsync не реплицирует | syncdev не применился при первом буте (гонка) | `ifconfig pfsync0 down/syncdev/up`; на последующих бутах — rc.conf |
| nuageinit: конфигурация не применяется | останавливается после стадии users (флейм первого бута) | повторная очистка/бут; документированная ручная починка через UFS-монтирование диска на здоровом узле |
| t01/t02 ложные FAIL | тесты фазы 1 ожидали реальный MAC lb1 и фильтр только SYN-ACK | t01 → ожидание 00:00:5e:00:01:01; фильтр → `tcp port 80` |

## 7. Ограничения

- CARP защищает только входящий путь: DSR-ответы идут мимо балансировщиков по определению режима.
- Health-check бэкендов в чистом pf отсутствует; вывод из пула выполняется `pfctl -T delete` (проверено t04). Автоматизация — возможное развитие (relayd поверх тех же таблиц).
- У FreeBSD-гостя не работает исходящий интернет (pkg/freebsd-update), что блокирует установку пакетов (doas); на функционирование DSR/CARP/pfsync не влияет.
- nuageinit нестабилен на первом буте: при пропуске конфигурации требуется повторный цикл `down/up` узла (вероятность оценочно ~50–75% на узел, проявлялась на 3 из 4 первых бутов lb1 и 0 из 1 у lb2).
